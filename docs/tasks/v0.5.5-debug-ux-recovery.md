## 1. P0 — 三语言 Debug 标准输入与完整交互（DEBUG-INPUT-01）

### 实机证据

用户在 Python \`HelloWorld.py\` 上放置断点，但在断点前调用 \`input("请输入你的名字：")\`；debugpy 输出提示后即抛 \`EOFError\` 并结束。用户无法在调试过程中向正在运行的程序输入文本。之前另一张照片中 \`SyntaxError: '(' was never closed\` 是用户源码的真实语法错误，**不可把语法错误算作 IDE 崩溃**。

现有代码经核查：
- \`native-library/src/Python/suik/adapters/dap.json\` 的 debugpy workflow 使用 \`"console":"internalConsole"\`、\`"redirectOutput":true\`。
- Java DAP workflow 也使用 \`"console":"internalConsole"\`。
- \`core/debug/.../DebugSession.kt\` 在处理 DAP reverse request 时仅支持 \`startDebugging\`，明确拒绝 \`runInTerminal\`。
- \`DebugController.kt\` 启动 DAP adapter 使用 \`spawnStdioProcess\`，其通信管道是调试协议，不可以当作用户程序的 stdin。
- LLDB DAP 的具体 input transport 需要按实际 adapter 支持能力实现，不能想当然视作 debugpy 的等价接口。

### 必须完成

1. 对 Python debugpy、Java Debug、C/C++ LLDB DAP 设计并落地支持交互式 stdin/stdout/stderr 的调试终端，复用现有 Ubuntu PRoot + PTY + TerminalSessionHost 的生命周期和 UI。
2. 在 DAP initialize capabilities 中**仅在宿主确实实现后**声明 \`supportsRunInTerminalRequest\`。完整实现安全解析 DAP \`runInTerminal\`（arguments、cwd、env、kind/argsCanBeInterpretedByShell、processId/shellProcessId、退出和清理）与规范要求的逆向响应，不接受任意包注入的未审阅路径/命令。未支持的参数有明确错误。
3. 在官方 Python/Java DAP workflow 中采用相应 adapter 实际支持的 integrated terminal 设置；C/C++ 需通过真实 lldb-dap 测试选用其兼容的终端方案。对不支持的 adapter 给出准确能力状态，而非假装可交互。
4. **双通道隔离**：DAP JSON 协议留在 adapter transport；用户输入/输出走真正的 PTY，不允许用 \`sendInput\` 将键入数据写进 DAP 协议进程，或仅往 UI 显示区追加假文本。
5. 项目调试和无 Project 单文件调试都要遵循已修复的 Host/Guest 路径映射和 bind，使用安全引号转义，支持中文、空格路径、已有 stdin 提示信息。
6. 在 Debug 活动时自动显示/聚焦对应终端但不覆盖正在使用的其他用户终端；提供清晰的“程序输入”焦点与输入发送。断点前、暂停时、继续后输入状态正确。程序退出显示真实退出码；停止/断开/重启时回收 adapter 和 debuggee 进程树，但保留已产生的日志与输出，绝不杀其他 Project/任务的进程。
7. 支持物理键盘 Enter、触屏输入法的编辑与回车、Unicode 中文输入及长文本粘贴。暂停后继续仍可交互；暂停本身不能让终端失去控制。
8. 原有断点、变量、调用栈、单步、继续、终止功能必须保持；不同语言断点只推送给其适配文件，不将无关语言文件提交给当前 adapter，避免仅显示 verified 但未命中。
9. 验收必须真实执行三份等待标准输入的程序：Python \`input()\`、Java \`Scanner.nextLine()\`、C/C++ \`scanf\` 或 \`std::getline\`；**输入前断点 / 输入后断点**、输入后继续、第二次调试、终止清理、同一任务输出保留都要实际测。错误输入与 EOF 的展示应真实且可诊断。
10. 不把 Build/Test 输入和 Debug 混淆；Build 主要非交互任务，测试脚本若确实请求输入则应明确处理而非静默卡住。

## 2. P1 — C++ Go to Definition 的 add 问题（CPP-LSP-02）

- 联想平板真实项目有 \`include/\`、\`src/main.cpp\`、\`src/math.cpp\`、\`src/c_math.c\` 等。对 \`add\` 使用跳转提示“未找到 add 的定义”。
- 不能仅凭截图宣称 clangd 坏了：先验证 \`add\` 在对应工程确实有一致的声明和定义，头文件被正确 include，符号调用在正确位置，且已更新到官方 C/C++ Kit 1.2.0。
- 对正确的 CMake 多文件工程：用真实 clangd 测 \`initialize\`、\`didOpen\`、\`didChange\`、\`textDocument/definition\` 返回的文件 URI/行列号、\`compile_commands.json\` 生成时机和 directory 真实可用、用户已打开文件的 Host/Guest 映射、多项目缓存以及跳转后的文件打开/焦点。
- 对声明与定义不符、工程没有索引或服务器未 Ready：明确显示不同原因（源代码缺少定义、正在索引、LSP 错误、结果为空），不笼统显示“未找到”。
- 如果项目本身没有定义，源码行为正确，则修复用户提示和诊断而不是伪造跳转目标。
- 验收：\`math.hpp\` 定义/声明、\`math.cpp\` 和 \`main.cpp\`，测试声明跳转、定义跳转、跨文件、中文目录、重开项目、修改源文件后刷新；Java/Python 跳转回归。

## 3. P1 — Build/Test/Run 任务完成结果与明确状态（TASK-RESULT-01）

- 用户图中的 Python Build 先输出 shell/任务包装脚本，回到提示符；Python Kit 使用 \`python3 -m compileall -q ...\`，静默成功是合理的，不能把没有输出认作失败。
- 需要在 Tasks/Output 或运行结果状态展示**任务名称、来源项目/文件、真实开始/结束、退出码、成功/失败/取消、耗时、日志位置**。保持原始终端输出但不要把包装脚本、环境变量/长随机 token 作为用户首要信息；避免泄露无关环境信息。
- Build/Test/Run 结果按会话、项目、工具区分；\`exit 0\` 确实成功才显示成功，非零 exit 失败，不可仅凭提示符返回推断。支持任务并发的归属匹配和停止、重跑；进程中断显示“已取消”，不能显示成功。Python \`compileall\` 静默通过应有显式状态。
- 验收：三语言 Build/Test/Run 各真实成功和失败案例、重复运行、输入相关案例、停止、退出码、输出保留。不得改变已有构建任务核心工作流程。

## 4. P1 — 平板布局紧凑、最大化与弹窗式管理（UI-LAYOUT-04）

实机照片中三栏 + 右侧主编辑区域 + 底部 Terminal/Debug 同时存在，使部分情况下可见工作区过小；大块 Packages/Kit 内容占满编辑区，底部终端也会压缩有效区域。

要求：
1. 保留现有第一栏导航、第二栏可拖拽宽度、主编辑器、底部 dock，用户保存的分栏尺寸、横竖屏操作和 UI 色彩。
2. 编辑器区及底部面板增加“一键最大化/恢复”，对应操作要明显；正常情况下支持收起 Files/侧栏（可一次恢复）和底部终端，必要时紧凑 Tab。
3. 对 IDE Kit 组件详单、依赖审阅、长安装日志、Settings 和其他长文本管理内容提供**响应式详情页/大对话框**选项；小可见区域/竖屏时使用宽/高受约束的可滚动大窗口或全屏 Sheet，不允许因固定尺寸裁剪按钮或内容。
4. Debug 交互终端、变量/栈/断点等需要持续操作的面板支持可调整高度和扩展的无阻断呈现；如果浮动窗口，只能是可操作的非模态容器，不能用普通模态 AlertDialog 将编辑器全部锁住。
5. 所有弹窗都需可关闭/返回、安全保持编辑状态与任务执行，键盘焦点不会乱跳，面板切换与最大化后的宽度持久化合理。测试 10~13 英寸横屏/竖屏、系统字体130%、软键盘弹出和分屏。
6. 暂不做新的全局视觉主题重绘、图标重设计或改名，避免 UI 修整引起启动/ANR 回归。
